# Shipping an Expo app to the stores

`expo-standalone-app-build` covers whether the code is *buildable*. This covers
getting the built thing in front of people.

Most of what follows is console work: a browser, an account, a form, or a wait.
It cannot be scripted. What CAN be scripted is listed first, along with the four
places it bites.

---

## Part 1 — `eas build`

### The config is evaluated LOCALLY before anything uploads

`eas build --profile production` runs `expo config` on the machine you are
standing on, *before* it talks to EAS. If the app's config has a production
guard that requires env vars, and those vars live in EAS-hosted environment
variables, **the build fails locally with an error that looks like a
misconfiguration and is not one.**

The fix is to source the production env locally for the config evaluation:

```bash
set -a; . ./prod.env; set +a      # or wherever the values live
export EXPO_NO_DOTENV=1           # or the dev .env loads on top and wins
npx eas-cli build --platform all --profile production --non-interactive --no-wait
```

`EXPO_NO_DOTENV=1` is not optional. Without it Expo loads `.env` — the DEV
tenant — over what you just exported, and inlines dev values into a build
labelled production.

**Verify before building, not after:**

```bash
node node_modules/expo/bin/cli config --json 2>/dev/null | python3 -c "
import json,sys; d=json.load(sys.stdin); d=d.get('expo',d)
print(d.get('name'), d.get('ios',{}).get('bundleIdentifier'), d.get('version'))"
```

If that prints the dev bundle id, stop.

### EAS archives from the GIT ROOT, not the project directory

This is the one that wastes the most time. If the Expo app is a subdirectory of a
git repo, the upload includes **the whole repo**. Anything sitting at the root —
agent worktrees, Python venvs, a second frontend, downloaded artifacts — is
uploaded too, and the cap is **2 GB**.

A real case: 53 GB of finished agent worktrees under `.claude/worktrees/` took a
project that should have been 87 MB and made it 2.9 GB. Rejected.

Before the first build of a session:

```bash
du -sh "$(git rev-parse --show-toplevel)"          # the number that matters
du -sh "$(git rev-parse --show-toplevel)"/* | sort -rh | head
```

**`.easignore` REPLACES `.gitignore` entirely.** Everything must be listed
explicitly, `node_modules/` included — the builder installs its own:

```
node_modules/
ios/
android/
.expo/
dist/
coverage/
test-results/
playwright-report/
```

Native directories are regenerated by EAS's own prebuild. Uploading them is
always waste and sometimes worse — a stale `ios/` gets built *instead of* a fresh
prebuild.

### Version numbers

- `autoIncrement: true` on the profile means EAS assigns build numbers. Nothing
  to bump by hand.
- **iOS and Android counters are independent.** iOS build 15 and Android version
  code 14 can be the same commit. Expect to be asked about this; it looks like a
  mistake and is not.
- A failed upload still increments. Gaps in the sequence are normal and harmless.

## Part 2 — `eas submit`

### iOS submits cleanly; Android usually cannot

iOS needs `ascAppId` and `appleTeamId` in `eas.json`'s `submit` block, and then
it is fully automatic. Apple processes for 5–10 minutes and emails when the build
reaches TestFlight.

**Android requires a Google service account key, and it cannot be created
non-interactively.** `eas submit --platform android --non-interactive` fails with
*"Google Service Account Keys cannot be set up in --non-interactive mode."*

Two ways past it:

1. **Have the human run `eas submit --platform android` interactively once.** It
   walks them through creating the key; every later submit is automated.
2. **Hand them the artifact.** Faster when they just want it shipped today:

```bash
npx eas-cli build:list --limit 1 --platform android --non-interactive --json \
  | python3 -c "import json,sys; print(json.load(sys.stdin)[0]['artifacts']['applicationArchiveUrl'])"
```

Download it to `~/Downloads` with a name that states the version, and tell them
the Play Console path. Do not just paste a URL — a downloaded file they can drag
is a smaller ask than a URL they have to fetch.

## Part 3 — TestFlight external testing

Internal testing needs no review but caps at 100 and requires every tester to be
an App Store Connect user on the team. External is the real channel: up to
10,000, but it goes through **Beta App Review** — a real human, a day or two.

### Test Information

App Store Connect → the app → TestFlight → **Test Information** in the left
sidebar. (If it is not there, the sidebar is collapsed — this has actually
happened.)

- **Feedback email**
- **Privacy Policy URL** — the form will not save without a *reachable* one.
  `curl -o /dev/null -w '%{http_code}'` it first; a 000 or 404 here is the most
  common reason this step stalls.
- **Description** — what testers see inside TestFlight.

### Sign-In Required, for an app with no username and password

An app using only Sign in with Apple / Google has no credentials to give, but the
sign-in genuinely IS required. Leave the box checked and put
`Sign in with Apple` in both the username and password fields, then explain
properly in **Notes**. Reviewers handle this routinely.

### If the app is invite-gated, the notes decide whether you pass

A reviewer who cannot get past a gate rejects the build. Put the code in the
notes, in plain words, with what to do:

```
The app is invite-only. After signing in you will be asked for an invite code.

Please use invite code: XXXXXXXX

There is no demo content — after joining, tap + to create an item.

Account deletion is in-app under Menu > Settings > Delete account, and at
https://example.com/delete-account
```

Naming the account-deletion path costs one line and removes a documented reason
to fail — reviewers look for it specifically.

### License Agreement: leave it EMPTY

Empty means Apple's standard EULA applies, which is what almost every app wants.
It is a legal document field, not a notes field — **anything typed there becomes
the licence users agree to.** A custom EULA is extra review surface and a reason
to come back at you.

### Groups persist; you do not make one per release

A group is a set of *people*. Builds are added to it. Build 15 goes to `Beta`,
gets reviewed, ships; build 16 goes to the same group. Subsequent builds within a
version are usually waved through in minutes — the slow review is the first one.

A second group is for giving *different people* a *different build*.

### Public link vs email invite — this decides who owns the onboarding

| | Apple emails the tester | You control the framing |
|---|---|---|
| Email invite | Yes — cold, generic, full of the word *beta* | No |
| **Public link** | **No** | **Yes** |

For real users rather than QA testers, use the public link and write the message
yourself. Apple's invite email is written for testers.

To make Apple silent entirely, also **uncheck "Automatically notify testers"** —
that is the only other mail it sends. The cost is that you must email people
yourself when you ship. For a small circle that is the point.

### Two things that bite people treating TestFlight as distribution

- **Builds expire after 90 days.** Every tester loses access when the build ages
  out. Treating TestFlight as a distribution channel means shipping at least
  quarterly or your users fall off a cliff.
- **TestFlight is a separate app they must install first.** For non-technical
  users this is where you lose them: they tap a link and get sent to install
  something they have never heard of.

## Part 4 — Google Play closed testing

Internal testing caps at 100 and needs each tester added by email. Closed testing
is the one that scales.

Play Console → Testing → **Closed testing** → the default `Alpha` track →
**Manage track**. (`Create new release` lives inside "Manage track", not beside
it.)

### Play Console navigation — verified 2026-09-06, because hunting for it wastes the owner's time

**There is a search box at the top of Play Console. Use it.** Typing "Main store
listing" or "App content" jumps straight there. Do this instead of walking the
menu, and tell the owner to do the same.

The sidebar, top to bottom: Dashboard · Statistics · Publishing overview ·
Protected with Play · **Test and release** · **Monitor and improve** ·
**Grow users** · Monetize with Play.

| What you want | Where it actually is |
|---|---|
| Create a closed-testing release | Test and release → Testing → Closed testing → the `Alpha` track → **Manage track**. "Create new release" is INSIDE "Manage track", not beside it. |
| Testers, countries/regions | Same track, as tabs alongside Releases. **Save before switching tabs** — Play discards unsaved changes. |
| The 9 declarations | **Monitor and improve → Policy and programs → App content.** NOT under "Test and release", which is where it sounds like it should be. |
| Store listing, icon, screenshots | **Grow users → Store presence → Main store listing.** |

**Never ask the owner to read you the menu.** If you cannot find something, say
you cannot see their screen and ask for a screenshot — you can read one. Making
someone transcribe a sidebar three times is the thing that turns a form-filling
session sour.

### Testers: use a Google Group, not an email list

An email list is edited in Play every time. A **Google Group** means Play points
at the group once and membership is managed at groups.google.com forever after.
Always the right answer when the tester list is not final — which it never is.

Creating one: groups.google.com → Create group → set **Who can join group** to
**Only invited users**, or anyone who finds it can add themselves and get the
app. The creator is added as owner automatically, so adding your own address in
the members box errors.

**Play matches the Google account signed in ON THE DEVICE**, not a preferred
contact address. This trips up nearly everyone.

Set the **feedback email** on the Testers tab too, and save before switching tabs
— Play will not carry unsaved changes across.

### The store listing gates the release

An app with an incomplete listing shows in the Play Store as its **package name
with no icon**. Fine for internal testing. **Closed testing will not publish
without:**

- App icon — 512×512 PNG
- Feature graphic — 1024×500
- At least 2 phone screenshots
- App name, short description (80 chars), full description (4000)

The feature graphic is the only one that needs designing; screenshots can be
generated from a simulator. Raise this BEFORE they start the closed-testing
flow — hitting it halfway through is worse than knowing in advance.

### THE BIGGEST TRAP: Play reviewers cannot use their own accounts

Apple's reviewers sign in with their own Apple ID. **Google's explicitly cannot** —
the Sign in details form says so outright:

> *"Reviewers are unable to create accounts, use their own existing accounts, or
> use free trials to access your app."*

So an app with only Google/Apple sign-in and no username/password still has to
hand Play **typeable credentials**. Advice that works for TestFlight ("the
reviewer uses their own account, here is the invite code") **fails on Play**.

**The fix needs no app change.** Create a dedicated Google account for review,
**turn 2-step verification off on it** (a reviewer cannot answer a challenge),
sign it into the app once if you can, and give Play that email and password. The
reviewer types them into *Google's own* sign-in sheet via "Add another account" —
your app never needs a password field.

Do NOT reach for "enable email/password auth" as the answer. If the sign-in
screen has no form, enabling the provider does nothing: you would also have to
build the form, which means a new screen, tests, a build and another review.

Fill the form as: **Name** `Reviewer account`, the credentials, and put anything
else (invite codes, where to tap) in **"Any other information required to access
your app"**.

### Starting a rollout does NOT send it for review

This one silently strands releases. Clicking **Start rollout to Closed testing**
leaves the track reading *"Not yet sent for review."* Play batches every pending
change — listing, declarations, release — and waits for one final submit:

**Publishing overview → "Send N changes for review".**

If a track still says "not yet sent for review" after a rollout, this is why.
Always finish here.

### The nine declarations under App content

For a private, ad-free, invite-only app the answers are nearly all the same.
Reason from the app's own privacy policy rather than guessing:

| Declaration | Answer for an app of this shape |
|---|---|
| Privacy policy | the live URL |
| Ads | No ads |
| Sign in details | see the trap above |
| Content ratings | IARC questionnaire — see below |
| Target audience | 13+ only. Ticking under-13 pulls you into Families policy |
| Data safety | the long one — see below |
| Advertising ID | No, if there are no ads or analytics SDKs |
| Government apps | No |
| Health apps | No — a prayer, journal or wellbeing app is not a "health feature" |

**Content ratings.** The category options are narrower than they look: *"Social or
Communication"* is defined as *"the primary purpose is to meet or communicate with
people."* An app where people share content but do not *meet* is **All Other App
Types**. Choosing that does not dodge anything — the interaction questions come
regardless, and **understating them is a real policy violation.** Answer Yes to
users interacting and to user-generated content; answer honestly on block, report
and whether interactions can be limited to invited people. "Chat moderation" means
filtering or reviewing content — block and report alone is **No**.

**Data safety.** Its encryption question is about **in transit**, not at rest.
Prove it rather than asserting it: check the API URL is `https://`, grep the
source for `http://`, and confirm the load balancer 301s. Then per data type,
collected Yes / shared No — data sent to Firebase or FCM is a *service provider
processing on your behalf*, which their rules do not count as sharing.

Two judgements worth making deliberately, both of which turn on *"do we collect
this as a field?"*: a profile photo that is only a **URL** from the OAuth provider
is not collecting Photos, and an app whose content happens to be religious is not
collecting **religious beliefs** unless it asks. Check the codebase before ticking
anything: a vestigial `phone_number` column that nothing ever writes must NOT be
declared, or the listing advertises data you do not hold.

### Store settings is a SEPARATE blocker from the store listing

The listing (name, descriptions, graphics) and **Store settings** (app category,
public contact details) are different pages, and a missing category surfaces only
as the unhelpful *"Your app cannot be published yet. Complete the steps listed on
the Dashboard."* Check the Dashboard task list when that error appears.

**The contact email is public and scrapeable**, and reviewers do sometimes write
to it. It should match the address on the privacy policy and terms — an
inconsistency is something a reviewer can notice. **Verify mail actually arrives.**
If the registrar charges for forwarding (GoDaddy does), **ImprovMX** is free and
keeps DNS where it is: two MX records plus one SPF TXT. Adding MX records does not
touch an existing A record, so the running app is unaffected.

### Screenshot geometry — pad, never crop

Phone screenshots must be **9:16**. A modern Android screenshot is commonly
**720x1600**, which is 1:2.22 and will be rejected. Pad the width to `height *
9/16` (1600 -> 900) with a colour **sampled from the app's own header**, so the
bars read as chrome rather than as letterboxing. Cropping loses content; padding
loses nothing.

**Screenshots leak real data.** A dev tenant usually holds real people's names and
real content, and store screenshots are public. Take them from a clean account
with invented content — the production build signed in as the review account is
ideal, since the consent screen is published there and the shots show what actually
ships.

### The other listing requirements

- **App icon** 512x512 PNG, **no transparency** — Play applies its own masking
- **Feature graphic** 1024x500
- **At least 2 phone screenshots**
- **Tablet / Chromebook / XR assets are OPTIONAL.** Omitting them produces a
  warning about form-factor optimisation, not a block. Do not supply tablet
  screenshots for an app that declares `supportsTablet: false`.
- **AI asset declaration** — if the icon or graphics were generated or rendered by
  AI (including a hand sketch cleaned up by an image model), label them. A
  screen capture of the running app is not a generated asset.
- The **"no deobfuscation file"** warning is harmless when you do not obfuscate.

### Free is a one-way door

An app listed **Free** on Play can never become paid. Monetize with in-app
products or subscriptions instead.

## Part 5 — Moving a personal account to a business account

The question arrives as *"what does it take to rebuild this under a business
account?"* — and the premise is usually wrong.

**Convert the account. Do not transfer the app, and do not build a second one.**

- **Apple** — developer.apple.com → Membership Details → *Convert to
  Organization*. Apps, certificates, TestFlight and the **Team ID** all survive;
  only the seller name changes.
- **Play** — Developer account → About you → verify company website → *Change
  account type*. Needs a new organization payments profile.
- **Both need a D-U-N-S number** for the entity, which must legally exist first.
  Free, one to two weeks. **This is the long pole and is independent of all app
  work** — start it early.

### Why transferring is materially worse

- An Apple transfer requires the app to have been **publicly released at least
  once**. A TestFlight-only app cannot transfer at all.
- A transfer re-scopes **Sign in with Apple** user identifiers, because they are
  scoped to the Team ID. Every Apple-signed-in account is orphaned unless
  migrated within 60 days. Conversion keeps the Team ID, so the problem never
  arises.
- A Play transfer keeps installs and reviews but drops tester lists.

### The bundle id does not change and does not need to

It stays whatever it is, even if it no longer matches the company name. Bundle
ids are opaque, users never see them, and no store requires them to match the
seller. **Changing one creates a genuinely new app** — never advise it for
cosmetic reasons.

## Over-the-air updates

Check whether `expo-updates` is installed before promising anything:

```bash
python3 -c "import json;print(json.load(open('package.json'))['dependencies'].get('expo-updates','NOT INSTALLED'))"
```

Without it there is no OTA at all — every change, including one word of copy,
needs a full build and a store round-trip. Say so plainly rather than letting
someone wait for an update that will never arrive.

Adding EAS Update is worth it for a project iterating on polish, but it is a
**native dependency**: adding it means another build and another review, and it
changes how the app boots. The right time is *after* review clears, not before.

## Red flags

| Thought | Reality |
|---|---|
| "The archive is only the app directory" | It is the whole git repo. Measure it. |
| "`.easignore` extends `.gitignore`" | It replaces it. List `node_modules/` yourself. |
| "iOS is 15 so Android should be 15" | Independent counters. Both are right. |
| "I'll script the Android submit" | Not without a service account key set up interactively first. |
| "I'll put a note in the License Agreement field" | It becomes the licence. Leave it empty. |
| "The reviewer will work out the invite code" | They will reject it. Put the code in the notes. |
| "Transfer the app to the business account" | Convert the account. Transfer needs a public release and orphans Apple sign-ins. |
| "They'll get the update automatically" | Only with `expo-updates`. Check. |
| "Store listing is a launch task" | Closed testing will not publish without it. |
